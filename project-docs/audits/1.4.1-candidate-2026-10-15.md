# Mahj 1.4.1 audit, corrected findings

Rechecked October 15, 2026 against app code at `5bb9bee`, version 1.4.1
(build 46). This replaces the earlier ranking of four P2 findings. That
ranking mixed an intentional reminder tradeoff, a measurement-definition
problem and two untested timing risks. It gave them more certainty and
uniform priority than the evidence supported.

The audit commits `61b5e07` and `5bb9bee` changed documentation and evidence
only. The reminder implementation is in the separate app commit `e8a8b26`.
The recommendation to use generic repeating copy was reasonable for keeping
an ongoing reminder truthful, but the audit did not measure its effect on
retention. It should not have implied a proven product improvement.

## Confirmed issues missed by the first audit

### Trial reminder: controls disappear at the largest accessibility text size

**Reproduced on iPhone 18 Pro, iOS 27.0.** The actual
`TrialReminderOfferView` was hosted in an iOS window at normal Large and
Accessibility XXXL (AX5), with matching UIKit and SwiftUI text-size settings.
At normal size both actions fit. At AX5 the long body fills the viewport,
the heading is truncated and both actions are outside the visible screen.
The view has no scroll container.

- [AX5 capture](1.4.1-recheck-evidence/trial-reminder-ax5.png)
- [Normal-size control capture](1.4.1-recheck-evidence/trial-reminder-large.png)

The capture used the shipping view with inert action closures, not a copied
layout. No purchase or notification-permission request was made. This proves
the component's layout failure, rather than an end-to-end sandbox purchase.
The screen is used after a trial starts in onboarding and on the paywall, so
this is more directly relevant to a paid user's experience than the earlier
speculative plan-selection race.

Fix direction: let the content and both actions scroll when they do not fit,
using the app's existing adaptive layout patterns. Verify both paths into
this view at AX5 before release sign-off.

### Trial relay: a transient upstream failure ends retries permanently

**Reproduced with mocked transport and database operations against the actual
relay function source.** A network exception or RevenueCat HTTP 429 escapes
`rc()`, is caught in `sweep()`, and writes terminal status `error`. Later
sweeps select only `pending`, so the row is never retried.

The probe ran two sweeps for each failure. Each case made exactly one
RevenueCat request, and the row remained `error` after the second sweep.
No real RevenueCat, Supabase or Meta request was sent.

The repository documents the relay as deployed in dry-run mode, with Meta
sending disabled. This affects relay reliability and its dry-run statistics;
it is not evidence of a broken training or purchase flow. Production rows
were not inspected in this recheck.

Fix direction: retain retryable failures as pending with bounded backoff and
an explicit retry policy. Recheck trial cancellation and consent before a
later send. Keep non-retryable errors distinct.

See [relay proof](1.4.1-recheck-evidence/relay-proof.txt) and its
[offline probe](1.4.1-recheck-evidence/relay-probe.mjs).

## Reassessment of the earlier findings

| Earlier finding | Corrected assessment |
|---|---|
| F01, finite reminder window | The discarded candidate really scheduled 42 daily or six weekly notifications. The source explicitly intended that cutoff. Calling it an unconditional P2 bug overstated a product tradeoff. Build 46 uses ongoing generic reminders, which preserve the preference and avoid stale counts. No retention benefit or harm was measured. |
| F02, CTA experiment exposure | A paywall impression is still used as a proxy for seeing an eligible trial CTA. This is a measurement-definition issue, not broken customer behavior. The actual readout filters customers by first-seen date, excluding ordinary existing customers, so the earlier historical-conversion warning was too broad. If the metric must mean an eligible CTA was visible, gate the exposure marker on that event. |
| F03, delayed churn prompt | Source shows consumption before a delay and no later presentation recheck. This remains an untested presentation risk, not a reproduced collision or lost report. 1.4.1 has no matching What's New entry, so that particular collision is dormant. A targeted Settings/navigation reproduction is still needed. |
| F04, mutable purchase plan | The task reads selection after an await while cards remain enabled. Capturing the tapped plan and disabling selection would be sensible hardening. No wrong-plan transaction was reproduced, and Apple's confirmation still displays the plan before the user approves a purchase. This should not have been presented as a confirmed billing regression. |

The first audit missed the post-purchase reminder layout. The build 46
follow-up also did not review the newly added relay implementation. The
successful build and unit suite did not cover those behaviors. The original
UI run was interrupted, so it could not support app-wide visual confidence.

## Fresh verification

- Two layout-capture tests completed on iOS 27. Their success means the
  captures were produced, not that the layouts passed: the AX5 image proves
  the defect above.
- The existing core UI capture run completed in 99.8 seconds with no missing
  navigation report. Eight representative frames were visually inspected:
  Home, Quick Session feedback, a graded Play a Hand discard, Read the Rack
  feedback, Keep or Throw card reveal, Charleston feedback, Reference and
  the Tile Room. These are sampled states, not complete drill runs.
- A free user opened `mahj://challenge`, answered the first question, then
  terminated and relaunched the app. The challenge showed
  **Resume at Question 2**. No membership purchase was needed.
- The relay probe reproduced terminal handling of both network failure and
  HTTP 429, using mocked dependencies only.
- A mocked readout check verified that a customer first seen before the
  release cutoff is excluded. This corrects the earlier F02 claim.
- The current full unit suite passed **226 tests, zero failures or skips**
  on iOS 27.0, after removing the temporary capture helper. See the
  [unit summary](1.4.1-recheck-evidence/unit-summary.json). The original
  231-test result belongs to the earlier candidate, before the reminder test
  changes, and must not be presented as the current build's test count.

The temporary layout test was removed from the app test target after
capture. No production behavior was changed during this recheck. Evidence
and reproduction details are indexed in
[the recheck evidence](1.4.1-recheck-evidence/README.md).

Real App Store trial eligibility, purchases, restore and renewal were not
exercised. iPad, landscape, hardware VoiceOver and the rest of the app at
large accessibility sizes remain outside this check. The two verified
issues above are actionable; the remaining source risks need targeted
reproduction before being promoted to confirmed regressions.
